Error page

Error pages replace a whole screen when the app cannot show it: not found, forbidden, server error, offline and session expired, each with one clear next step.

WCAG 2.2 AAStatus: stableSince v1.0

Overview

An error page is used when the page itself cannot be shown: the link is wrong (404), the person may not open it (403), the server failed (500), the device has no connection, or the session ended. It reuses the empty state inside a .card-plain in the app shell, or the auth card layout when the person is signed out.

A failure of one region of a working page is an empty state in its error form; a failed action is a toast or alert; a field problem is an inline message. Every error page has one primary action that gets the person back to work, and it always says that their days are safe when that is true.

Anatomy

  1. Icon badgeA glyph that matches the cause (calendar, lock, alert, cloud-off), aria-hidden.
  2. Title (h1)The only h1 on the page: says what happened in plain words.
  3. TextOne or two sentences: why, and what is safe. May include an error reference.
  4. ActionsPrimary recovery action first, then a secondary route back to the calendar.
  5. Card (optional).card-plain frames the message inside main.shell; signed-out pages use .auth-layout and .auth-card instead.

Variants

Five pages, one structure. The title is the h1 of the page.

Sizes

Error pages are not sized by a modifier. The card is as wide as main.shell (--layout-container-max at wide widths) and the text is capped at 36ch; the auth variant is capped at 26rem by .auth-card (36rem with .auth-card--wide). Height follows the content, with .empty padding of --space-12.

  • Retry: Try again re-requests the page. While it runs show a busy button (button), not a new page.
  • Recovered: when the retry succeeds, replace the error page with the requested page; do not leave the person on a success message.
  • Offline returns to the page automatically when the connection comes back, if it can; the button stays for when it cannot.

Responsive behaviour

  • The error card is full width inside the shell on phones (page padding --layout-margin) and centres from 768px; the empty column is capped at 36ch text width.
  • Actions wrap: at 360px Try again and Back to calendar stack, primary first.
  • .auth-layout centres the card in the viewport with min-height: 100dvh and padding of --space-6 by --layout-margin.
  • Keep the top bar on app error pages so the person can navigate away; hide it only on signed-out pages.

Theming

Error pages add no tokens of their own: the card is --color-bg-surface with --color-border-default and --radius-lg, and the contents are the empty state's. The tone shown for server errors is the danger pair used by .empty--error; not-found, forbidden and offline stay neutral on purpose, because they are not the person's fault or the product's failure to be alarmed about.

.card-plain { background: var(--color-bg-surface); border: 1px solid var(--color-border-default); border-radius: var(--radius-lg); }

Accessibility

Role and pattern

A normal page with a main landmark and a single h1 (the title), not an alert dialog. Set the document <title> to the title ("This page doesn’t exist — Greenlit"). Do not use role="alert" for a full page: the route change announcement already tells assistive technology the page changed, and the app focuses the heading.

Keyboard

KeyAction
TabMoves through the top bar, then the actions. The first action is the recovery.
Enter, SpaceActivates a button action; Enter follows a link action.

Focus

On arrival, move focus to the h1 (tabindex="-1") so the message is read first and Tab then reaches the actions. The skip link still works. Never autofocus the retry button: a screen-reader user should hear what happened before being offered a button.

Labelling

The title and text carry the meaning; the glyph is aria-hidden and the danger tint is redundant. The error reference ("7F3A-91C2") is real text so it can be copied and read out. Links and buttons say where they go: "Back to calendar", not "Home" or "Go back".

Contrast

Title on surface
Text on surface
Error icon on danger tint
Card border on page

Motion

Error pages have no animation of their own. Their buttons use the standard hover and busy transitions, which collapse under prefers-reduced-motion. Do not auto-retry in a loop that flashes the page; if you retry in the background, say so in text.

Touch

Actions are medium (40px) or large (48px on the auth card) buttons, 12px apart, centred and easy to reach with a thumb. No gesture (pull to refresh) is the only way to retry.

Content

  • Not found: "This page doesn’t exist" / "The link may be old or mistyped." Never "404 Not Found".
  • Forbidden: "You don’t have access to this" / "Only managers can open this page. Ask Maya Chen if you need it." Name the role and a person who can help.
  • Server error: "Something went wrong on our side" / reassure ("Your days are safe.") / show an error reference. Offer Try again.
  • Offline: "You’re offline" / "Check your connection. Greenlit will pick up where you left off, and nothing you’ve seen has changed."
  • Session expired: "Your session has expired" / "For your security you were signed out after a while away. Sign in again to pick up where you left off."
  • Plain words, no jargon, no blame, no jokes. The primary action is always a way back to work.
