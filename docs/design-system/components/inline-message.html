Inline message

Inline messages sit next to the thing they describe: field help, field errors, a form-level error summary and a short saved or failed status.

WCAG 2.2 AAStatus: stableSince v1.0

Overview

An inline message is text placed in the flow, beside the control it explains. There are four: .field__help (guidance before the mistake), .field__error (the mistake, after validation), .form-summary (all the mistakes at the top of the form) and .inline-status (a small saved, failed or neutral status beside a button).

Field help and error belong to the form field, which wires them to the control with aria-describedby; this page documents the messages themselves. For a message about the page rather than a field use an alert; for the result of an action use a toast.

Anatomy

  1. Label and controlOwned by the form field; the control is aria-invalid="true" when an error is shown.
  2. Help text.field__help: muted body-sm text, referenced by aria-describedby.
  3. Error text.field__error: danger colour with a leading warning glyph drawn by CSS, so the error is never colour alone.

Variants

Sizes

Inline messages take the body-small type size (--text-body-sm, 14px) and inherit the width of their field. The inline status icon is 1rem (.icon--sm). There are no size modifiers: a message long enough to need one belongs in an alert.

States

Messages come and go with validation and saving. They share the field's width and add no layout jump when the field reserves their space.

  • Help is always present; it never replaces the label and never becomes the only place a rule is stated.
  • Error replaces nothing: the label and value stay. Validate on blur, then on every change once an error has shown; show the summary only on submit.
  • Inline status has three states: neutral, success and danger. It is not a toast, so it stays next to its button until the next action.

Responsive behaviour

  • Messages wrap with their field; they never truncate or scroll, and the error glyph stays on the first line (align-items: flex-start).
  • In a form layout grid (.form-grid--2|3 from 640px) every field reserves its own message line, so errors do not push neighbours.
  • The summary sits above the form at every width; its list of links wraps and stays tappable (links are body-sm text with a 24px minimum target through line height).
  • Inline status sits beside its button when there is room and wraps below it on a phone.

Theming

Help reads --color-fg-muted; errors and the danger status read --color-danger-fg; the success status reads --color-success-fg. All three are retuned per theme (700 in light, 300 in dark) so each keeps at least 4.5:1 on the surface. The summary reuses the alert tokens and adds a 4px --color-danger-solid left bar.

.field__error { color: var(--color-danger-fg); }
.form-summary { border-left: 4px solid var(--color-danger-solid); }

Accessibility

Role and pattern

Help and error text are associated with the control through aria-describedby (ids, space separated) and the control carries aria-invalid="true" while it has an error (WAI-ARIA authoring practice for form validation). The form summary is role="alert" and is focusable (tabindex="-1") so it can receive focus on submit. An inline status is announced through a polite live region (role="status").

Keyboard

KeyAction
TabMoves from the control to the next control; help and error text are not tab stops.
EnterOn a link in the summary, moves focus to the failing field.
Enter / SpaceOn the submit button, validates; if errors exist the summary takes focus.

Focus

On a failed submit move focus to the summary (tabindex="-1"), not to the first field, so the screen reader reads the count and the list first; the links in the list then move focus to each field. Single-field errors keep focus on the control.

Labelling

Reading order for a control is label, value, state, help, error. Error text starts with the instruction ("Enter your email address"), not "Invalid". The ⚠ glyph is generated content and is not spoken; the words carry the meaning. Never use title or placeholder text as the message.

Motion

Inline messages appear without animation, so nothing changes under prefers-reduced-motion. Do not fade errors in: they are the result of an action and should appear instantly.

Touch

Summary links are body-small text on their own lines with at least --space-1 between items, which gives a target above 24px high. The inline status is not interactive.

Content

  • Help: say what the field is for or its format, in one sentence: "This is how you sign in.", "This is where your invitation was sent."
  • Error formula: what to do, then the example if needed: "Enter your email address." "Enter a full email address, like finn@northwind.studio." Never "Invalid input".
  • Summary: "Fix 2 things to continue" followed by the same wording as each field error, each linking to its field.
  • Status: a past participle: "Password updated", "Couldn’t save". No exclamation marks.
  • Sentence case, curly apostrophes, no blame ("Enter" rather than "You forgot").
