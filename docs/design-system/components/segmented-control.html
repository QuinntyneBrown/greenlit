Segmented control

A segmented control picks exactly one option from a short, always-visible set. In Greenlit it is the paint picker on the calendar; the same file also holds the joined button group for independent toggles.

WCAG 2.2 AAStatus: stableSince v1.0

Overview

Use a segmented control when the user chooses one of two to six mutually exclusive options and the choice takes effect immediately, such as which status to paint onto the sheet (Select, Confirmed, Requested, Tentative, Clear). The options are all visible, the current one is obvious, and changing it is one tap.

It is not navigation (use tabs), not a form answer to be submitted later (use a radio group) and not for more than about six options (use a select). A single on/off preference is a switch; a lone toggle such as a sort order is a button with aria-pressed.

The same file styles .btn-group: buttons fused into one bar where each button is an independent pressed toggle (aria-pressed), so zero, one or several can be on. Choose by semantics, not looks: exclusive choice means a segmented control, independent toggles mean a button group.

Anatomy

  1. Group label.paint-picker__label. Names the group; the control references it with aria-labelledby.
  2. Track.segmented: role="radiogroup", 1px border, --radius-md, scrolls horizontally rather than wrapping.
  3. Checked segmentaria-checked="true" inverts to --color-fg-default on --color-bg-surface.
  4. Swatch and labelA status swatch (.swatch[data-status]) plus the status word. The word carries the state; the colour only repeats it.

One visual form, three content shapes.

Paint picker: icon or status swatch plus text. The swatch is decoration, the word is the name.

Button group (independent toggles)

.btn-group with role="group" and aria-pressed on each button. Any combination can be on, so the pressed state is the label plus a tinted background, not colour alone.
HTML

Sizes

One size. Segments are --control-height-sm (32px) high on a fine pointer and grow to --target-comfortable (44px) under @media (pointer: coarse), so touch users get a comfortable target without a size prop. .btn-group follows the button sizes (.btn--sm, default, .btn--lg).

States

The checked state is exposed with aria-checked (radio) or aria-pressed (toggle), never with a class. Hover and focus are forced with data-state for review; the pages use :hover and :focus-visible.

Both themes

  • The checked segment inverts rather than tints, so it stays distinguishable in forced-colors mode and for users who cannot tell the status colours apart.
  • There is no loading or error state. If the choice triggers a request, show progress on the surface the choice affects, not on the control.
  • Disabled segments use the native disabled attribute at 50% opacity and leave the tab order.

Responsive behaviour

  • The track is inline-flex with max-width: 100% and overflow-x: auto. At 360px the five paint options scroll sideways inside the track instead of wrapping or pushing the page wide.
  • .paint-picker keeps min-width: 0 so the toolbar row that contains it can shrink; the label stays on the same line as the track.
  • On touch devices (pointer: coarse) segments grow to 44px high. Labels never truncate; white-space: nowrap keeps each segment on one line.
  • Never switch the control to a dropdown at small widths: the sheet needs the current paint status visible while painting.

Theming

The control reads only semantic tokens: --color-bg-surface and --color-border-default for the track, --color-fg-muted for unchecked labels, --color-bg-subtle for hover, and --color-fg-default on --color-bg-surface (swapped) for the checked segment. Both themes therefore invert automatically: a dark checked segment on a light track, and the reverse.

/* Tint the checked segment with the accent instead of inverting */
.segmented__btn[aria-checked="true"] { background: var(--color-accent); color: var(--color-fg-on-accent); }

Accessibility

Role and pattern

WAI-ARIA APG Radio Group: role="radiogroup" with aria-labelledby on the track, role="radio" and aria-checked on each segment. The button group follows the toggle Button pattern: role="group" with aria-pressed on each button.

Keyboard

KeyAction
TabMoves into the group onto the checked segment (roving tabindex: only one segment is in the tab order), then out of it.
→ / ↓Moves focus to the next segment and checks it; wraps from last to first.
← / ↑Moves focus to the previous segment and checks it; wraps.
SpaceChecks the focused segment if it is not already checked.
Space / Enter (button group)Toggles aria-pressed on the focused button; Tab moves between buttons.

Focus

The shared focus ring is drawn around the focused segment, offset into the track. Because arrow keys check as they move, focus and selection always agree; do not decouple them.

Labelling

The group is named by its visible label (aria-labelledby="paint-label"); a group with no visible label uses aria-label. Each segment's name is its text. The status swatch is aria-hidden so "Confirmed" is read once. Never rely on the swatch colour to tell options apart.

Motion

No animation: the checked segment changes colour instantly. Nothing needs a reduced-motion override.

Touch

44px segments on coarse pointers (WCAG 2.5.8 comfortably exceeded), 2px gaps inside a padded track. Painting is also possible without the control by tapping cells, so the picker is a shortcut, not a gate.

Content

  • Labels are one word, a noun or status name, in sentence case: "Confirmed", "Month". Not "Show confirmed days".
  • Use the domain's status words exactly: Confirmed, Requested, Tentative. "Clear" removes a day; do not call it "Delete" or "None".
  • Keep labels about the same length so segments look balanced. Two to five options; more than six becomes a select.
  • The group label states what the choice controls ("Paint", "View"), not the control type.
