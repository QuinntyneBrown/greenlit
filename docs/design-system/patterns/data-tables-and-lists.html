Pattern

Data tables and lists

Choosing between the sheet, a table, a list and a request row, and making each one readable, sortable and operable by keyboard.

WCAG 2.2 AAStatus: stable

Overview

Most of Greenlit's data is the sheet. Everything else is a short list of people or requests: fewer than ten people per team means no paging, no column resizing, no virtualization. The patterns below keep those small views consistent. Components: table, list, description list, member list, request row, avatar, badge, pagination.

When to use which

The data isUseWhy
Days by member by dateTeam grid (the sheet)The product. Colour and symbol per cell.
Months of the year at a glanceYear grid with sliversShows the shape of the year, not the detail.
Numbers to compare across membersTableColumns align for scanning.
Items that need a decisionRequest rowsThe decision buttons live in the row.
People with editable fieldsMember listControls inside a list row.
Label and value for one entityDescription listFacts about one request or member.
A few homogeneous itemsListHolidays, runs of days.
  • If the user compares values across rows, use a table. If they act on each row, use a list. If they read it as a sequence of days, use a run list or the sheet.
  • Do not use a table for layout.

Structure

Greenlit shows data in four shapes. The sheet (team grid) is for time, table is for comparing numbers, request rows are for deciding, and member list is for people with controls.

Responsive behaviour

  • 360px: tables sit in a horizontally scrolling wrapper whose first column (the name) stays readable; request rows stack: person, note, actions. Checkbox stays at the start.
  • 768px: request rows become a grid: person, note and meta, actions right-aligned.
  • 1024px and up: tables fill the container with sticky header; the sheet shows a month with no horizontal scroll when the container is wide enough, otherwise it scrolls inside its card.
  • Never hide a column on mobile without moving its content into another one; an allowance table keeps Left visible.

Accessibility

  • Real <table> with <caption> (can be visually hidden), scope="col"/"row". Never use ARIA grid for a read-only table.
  • Sortable headers contain a <button>; aria-sort is on the th. Changing the sort announces nothing extra; the arrow and the attribute carry it.
  • The horizontal scroll wrapper has tabindex="0", role="region" and a name so keyboard users can scroll it.
  • Every control in a row is named for the row: "Adjust allowance for Ben Okafor", "Select Ana Ruiz's request".
  • Row actions revealed on hover must also appear on :focus-within.
  • Lists of interactive rows are ul/li; the primary action is the name, not the whole row, unless the whole row has one action.
  • Numbers are never colour-only: negative has a minus sign.

Content

  • Column headers are nouns, sentence case, short: Member, Allowance, Used, Left.
  • Dates in rows are short ("16–20 Nov") with the day count after a dot ("5 days"). Singular: "1 day".
  • Empty cells show an em dash with a hidden "none" for screen readers, never blank.
  • Row action labels are verbs ("Adjust", "Approve"), with the person in the accessible name.
