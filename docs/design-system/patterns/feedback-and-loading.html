Pattern

Feedback and loading

Tell the user the app heard them: skeletons while a region loads, a busy button while an action runs, words when it is done.

WCAG 2.2 AAStatus: stable

Overview

Greenlit is a shared sheet; people glance at it, tap a day and move on. Feedback must therefore be fast, local and quiet. Show it where the user acted, keep the layout still, and say the outcome in text.

Compose from skeleton, spinner, progress bar, inline message, toast and the busy state of button. Failures continue in Empty and error states.

When to use which

WaitUseWhy
Under 100 msNothingInstant changes need no extra motion. The cell just changes colour.
Painting a dayOptimistic update, then roll back with an error toastThe sheet is the product; it must feel immediate.
Button action, 0.1 to 3 sBusy button (aria-busy)The feedback sits under the user's finger.
Region first loadSkeleton that matches the layoutNo layout shift; sets expectations.
Known totalProgress barAllowance usage and imports, never as decoration.
Button inside a small spaceSpinnerBanners and the connection status use a spinner.
Over 10 sKeep the skeleton, add a sentence and a retryStop implying that progress is coming.
  • Never block the whole page with a full-screen spinner. At most one region is replaced by a skeleton at a time.
  • A result the user must not miss (a failure) is a persistent message; a result they caused and can see (a colour changed) is at most a toast.

Structure

A typical view moves through three feedback layers: the region shows a skeleton while it loads, the pressed button shows busy while its request runs, and a status line or toast reports the result.

States

PhaseWhat showsWhat is announced
IdleThe contentNothing
LoadingSkeleton in the region; controls for that region disabled"Loading the calendar" once
BusySpinner in the pressed button; width unchangedNothing extra; aria-busy is read on focus
SuccessContent updated; a toast when the change is not visible where the user isToast text through the polite live region
FailureInline message or error empty state; input is keptAlert text, once
SlowAfter 10 s add: "This is taking longer than usual." with RetryPolite status
  • Skeletons animate with a shimmer that stops under prefers-reduced-motion; the shape still communicates loading.
  • A skeleton never stands in for an error or an empty result.

Responsive behaviour

  • 360px: skeleton rows are full width and the sheet skeleton scrolls inside its card like the real sheet. Busy buttons in a block footer keep their full width.
  • 768px: the same skeleton in the same position; do not add extra columns just to fill space.
  • 1024px and up: toasts appear bottom right, 24rem wide; on narrow screens they span the width above the selection bar.
  • Reserve the height of the region (min-height from the layout) so loading to loaded never shifts the page.

Accessibility

  • Exactly one polite live region per concern: one role="status" for the loading sentence, the toast region for results. Do not put aria-live on skeleton elements.
  • Mark skeleton shapes aria-hidden="true"; mark the loading container aria-busy="true" and clear it when done.
  • A busy button keeps its accessible name; it stays focusable so focus is not lost, and ignores activations.
  • After a region loads, do not move focus unless the user's last action opened it.
  • A progress bar has role="progressbar" with a name and aria-valuenow/min/max; the number is also written next to it.
  • Motion respects prefers-reduced-motion.

Content

  • Loading sentences name the thing: "Loading the calendar", "Loading requests". Not "Please wait".
  • Inline progress is a present participle with an ellipsis: "Saving…". The result replaces it: "Saved just now".
  • Failure follows the formula: what happened, why if known, what to do, and whether anything changed: "Not saved. Check your connection and try again."
  • No exclamation marks, no humour while something is broken.
