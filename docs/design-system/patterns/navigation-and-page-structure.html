Navigation and page structure

The frame around every screen: shell, top bar, main navigation, page title row, and how users move between and within screens.

WCAG 2.2 AAStatus: stable

Overview

Greenlit has four destinations (Calendar, Year, Requests, Settings) and one account menu. The structure is flat on purpose: a manager of ten people should never wonder where they are. Navigation is built from top bar, app navigation, period navigation, skip link, tabs, back link and pagination.

When to use which

NeedUseNot
Switch between product areasApp navigation in the top barTabs, which are for views of one thing
Move in timePeriod navigation: previous / next, title as the current periodDate pickers on the sheet
Switch views of one entityTabsLinks to separate pages that look like tabs
Return to a parentBack link with the destination's nameThe browser back button as the only way
Sections of one long pageSettings navigation (in-page anchors)A nested app navigation
Account actionsMenu from the avatar buttonExtra top-level links
Long listsPaginationInfinite scroll; the sheet and lists are small
  • Bare shell for anything that happens before a team exists or after the session ends. App shell for everything else.
  • The member and manager see the same navigation; manager-only content inside a page is hidden or read-only, not a different menu.

Structure

Every signed-in screen has the same frame: skip link, top bar with brand, main navigation, team name and account menu, then main containing a page-title row (period navigation on the left, the page's tools on the right) and the content.

Responsive behaviour

  • 360px: the brand and account menu share the first row; the main navigation drops to a second, full-width row that scrolls horizontally without a visible scrollbar. The team name is hidden. Page title row wraps: title first, tools under it.
  • 768px: navigation joins the brand row. Team name appears from 640px.
  • 1024px and up: content is centred in the container (--layout-container-max); the settings navigation becomes a side column.
  • Navigation targets are at least 44px tall on touch; period arrows are icon buttons with 44px hit areas.

Accessibility

  • Landmarks: header, nav aria-label="Main", main id="main". Any second nav has a different label (Breadcrumb, Settings sections).
  • First tab stop is the skip link, targeting #main. Focus order is brand, main navigation, team, account menu, then content.
  • One h1 per page: the period title, the page name, or the person's name. Do not skip heading levels.
  • On a route change, move focus to the new h1 (tabindex="-1") and set document.title. Announce nothing extra.
  • Tabs follow the ARIA tab pattern: Left and Right move between tabs, Home and End jump, only the selected tab is in the tab order.
  • Previous and next month buttons name the target month once the title changes ("Previous month" stays stable; the new title is read by the heading change).

Content

  • Destination names are single nouns: Calendar, Year, Requests, Settings. No verbs, no icons without text.
  • Page title is the thing on screen: "November 2026", "Requests", "Settings", the person's name.
  • Back links name the destination: "Back to calendar", never just "Back".
  • Document title: "Page · Team name · Greenlit".
