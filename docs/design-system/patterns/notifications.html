Notifications

Toast, banner, alert and inline message: which channel to choose, how long it lives and how it is announced.

WCAG 2.2 AAStatus: stable

  • When to use which
  • Structure
  • States
  • Responsive behaviour

Overview

Greenlit notifies about four kinds of thing: the result of an action (days confirmed, request sent), a change from another person (a request arrived), a condition of the app (offline, session ending) and a problem with a form or a section. Each has one channel. Components: toast, alert and banner, inline message, badge (the pending count).

When to use which

KindChannelLivesVariants
Result of the user's own actionToast8 s, pauses on hover/focussuccess, info; Undo for reversible changes
Warning after an actionToast, warning8 swarning
Failed action with no form to host itToast, dangerUntil dismisseddanger, with Try again
App condition (offline, unstable)BannerUntil resolvedinfo, warning, danger, success on recovery
Problem inside a dialog or sectionAlert at the top of that containerUntil fixed or retrieddanger, warning
Work waiting for the managerCount pill on Requests; never a toastUntil handledcount
Needs a decision before continuingA dialog, not a notificationUntil answered-
  • Two toasts at most are visible; extras queue. Three simultaneous messages mean the design is wrong.
  • Do not use a toast for something the user cannot act on and cannot see elsewhere; use the inline alert.

Structure

Three channels, ordered by interruption. Toasts report what just happened; banners report a standing condition; inline alerts report a problem with the thing in front of the user.

Responsive behaviour

  • 360px: the toast region spans the width with a 16px gutter, above the selection bar when one is showing. Action and dismiss buttons keep 44px targets. Banner text wraps; the dismiss stays top right.
  • 768px: toasts are 24rem wide, bottom right, 24px from the corner. Banners are full width.
  • 1024px and up: unchanged; the region never covers the sheet's first column or the top bar.
  • Under a keyboard or zoom of 400% the toast still fits: it wraps text, never truncates it.

Accessibility

  • One live region. The toast region exists in the DOM from page load with role="status" aria-live="polite"; inserting a toast inside it announces it. Danger toasts use role="alert". A region that is created at the same time as its message is often not announced.
  • Never move focus to a toast. If it carries an action, the action is reachable in tab order after the sheet; Undo is also available as a keyboard shortcut in the same order.
  • The timer pauses on hover and while focus is inside. Messages the user must read (errors) do not time out. Users can dismiss any toast with a named button ("Dismiss").
  • Banners that appear in response to events are role="status" or role="alert" by severity; those present on load are plain content.
  • Each variant has an icon and a title, so no state is colour-only. Contrast of text on the toast surface is at least 4.5:1 in both themes.
  • Respect prefers-reduced-motion: toasts fade instead of sliding.

Content

  • Title is a past-tense statement of the result: "3 days marked confirmed for Ana", "Request sent". Text (optional) adds what happens next.
  • Name the people and the number of days; avoid "successfully".
  • Action is one word or two: "Undo", "Try again". Never "Click here".
  • Failure formula: what happened + what to do + whether anything changed: "We couldn't send your request. Check your connection and try again."
  • Banners state the condition then the consequence: "Your connection is unstable. Changes may take a moment to save." Recovery replaces it with "You're back online" for a few seconds.
