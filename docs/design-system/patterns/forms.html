Forms

How Greenlit forms are composed, validated and submitted: labels, help, errors, the summary and the footer.

WCAG 2.2 AAStatus: stable

Overview

Greenlit has few forms and each is short: sign in, create a team, invite a member, request time off, add a holiday, adjust an allowance, the settings sections. The pattern keeps them uniform so a manager who has learned one has learned all.

Build forms from form field (label, control, help, error), form layout and the controls: text field, textarea, select, checkbox, radio group, switch and counter. Submit with a button.

When to use which

Pick the container by how much context the task needs and how long it lives.

FormUse forContainerSubmit behaviour
Dialog formA short task started from a button: request time off, invite, add holiday, decline with a reasonDialog, 1 to 4 fieldsFooter primary; the dialog stays open and busy until the server answers
Auth cardSign in, create team, accept invite, reset password.auth-card on its own bare-shell pageOne block primary on narrow screens; link to the sibling task underneath
Settings sectionStanding configuration: team name, time zone, work week, allowances.settings-section with fieldsetSection-level Save; a success toast, not a page reload
Drawer formEditing one entity with many fields while the sheet stays visibleDrawerSame footer rules as a dialog
  • Fewer than five fields and started by a button: dialog. Never expand a form in place on the page.
  • Reached by a link or a route, with no sheet behind it: its own screen.
  • Changing a setting that applies instantly and is reversible: a switch with a toast, no form at all.

Structure

The reference composition is the Request time off dialog in its invalid state: a header that names the task and says who is affected, a danger summary that links to each broken field, the fields in a .form-grid, and a footer whose primary button stays last. Forms never sit inline on a page; a button opens a dialog or navigates to a screen.

Validation timing

Fields validate on blur, once, then re-validate on every change until valid. The summary appears on a submit attempt and lists every failing field as a link to that field.

States

StateWhat the user seesMarkup
PristineLabels, optional help, enabled submit. No errors are shown before the user has acted..field only
Field invalidRed border, the warning glyph and an error sentence under the field.aria-invalid="true" + aria-describedby to .field__error
SummaryDanger alert at the top of the body naming how many things to fix, each linking to its field..alert.alert--danger.form-summary, role="alert"

SuccessThe dialog closes and a toast confirms. On an auth card the card is replaced by a success message.Toast
  • Never disable a field to mean busy; use readonly so values stay selectable and announced.
  • The form keeps the user's input after a failure, a password included, so a typo can be corrected rather than retyped (as on the sign-in error state).

Responsive behaviour

  • 360px: one column. .form-grid--2 collapses automatically; dialogs become bottom sheets with the footer pinned (position: sticky); auth-card primary is btn--block.
  • 768px: two-column grids for paired fields (first day / last day, role / yearly days). Dialogs centre at 32rem.
  • 1024px and up: settings sections sit beside the settings navigation; field width never exceeds 32rem, so lines of help text stay short.
  • Inputs are at least 16px so mobile browsers do not zoom on focus; controls are at least 40px tall.

Accessibility

  • Every control has a visible <label for>. A placeholder is an example, never the label. Table-like rows of inputs (member roles) use a visually hidden label naming the person.
  • Focus on open: the first field (autofocus) or, for a confirmation, the safest button. Focus on submit failure: the error summary; each link moves focus to its field.
  • Announce: the summary uses role="alert"; field errors are read because the field's aria-describedby points to them. Do not also make each field error a live region.
  • Order: DOM order is visual order. Required is the default, so only optional fields are marked, in text: "(optional)".
  • Group related controls (radio sets, the work week) in a fieldset with a legend.
  • Never rely on the red border alone: the error text and the warning glyph carry the state.

Controls follow their component pages: text field, select, radio group.

Content

  • Labels are nouns in sentence case: "First day", "Team name". No colons, no "Please enter".
  • Error formula: what is wrong, then what to do. "Pick a day on or after the first day." Not "Invalid date".
  • Summary title: "Fix 1 thing to continue" / "Fix 3 things to continue".
  • Help says why or what for, once: "Weekends and holidays are worked out in this time zone."
  • Primary button is the verb of the task: "Send request", "Invite member", "Add holiday", not "Submit" or "OK".
  • Cancel is "Cancel" unless the dialog is a confirmation, where the safe option names the outcome: "Keep pending".
